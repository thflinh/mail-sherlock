1. PROJECT OVERVIEW
================================================================================

Mail-Sherlock is a full-stack AI-powered email search tool that allows users to
find Gmail messages using natural language descriptions instead of exact keyword
matching. Rather than trying to recall the precise subject line or sender name
of an email, a user can describe what they remember about it — e.g., "the
invoice from my cloud provider last month" — and the system returns ranked
results based on semantic meaning.

The project consists of three main components:
  - A Python/FastAPI backend that handles Gmail sync, embedding generation,
    OAuth authentication, and AI-enhanced search.
  - A React/TypeScript web application providing a dashboard and landing page.
  - A Chrome Extension (Manifest V3) for quick in-browser access to search
    while using Gmail.

All embedding computations run locally on the user's machine, making the
system privacy-preserving by design. Email content is never sent to third-party
embedding services.


================================================================================
2. MOTIVATION & PROBLEM STATEMENT
================================================================================

Standard email search tools (including Gmail's built-in search) rely on
keyword matching. This works well when users remember the exact words used in
an email, but fails when:
  - The user remembers the *topic* or *context* but not exact phrasing.
  - Emails are long and the relevant part is buried in the body.
  - The user wants to search across multiple accounts simultaneously.
  - Search terms are too generic and return hundreds of irrelevant results.

AI-powered email assistants like Gemini in Gmail or Microsoft Copilot can
answer questions about email, but they:
  - Require sending email content to third-party cloud services.
  - Do not allow transparent control over what is indexed.
  - Are locked behind subscription tiers or specific platform integrations.

Mail-Sherlock addresses these gaps by:
  - Running sentence-embedding models locally (all-MiniLM-L6-v2, ~90MB).
  - Indexing email content in a local/self-hosted MongoDB instance.
  - Using Gemini only for lightweight query intent parsing (not email content).
  - Providing a simple, open interface via both a web app and Chrome extension.

High-Level Architecture:

  |  (React MV3 Popup) |    |   (React SPA)     |    |   (React Route)   |
  +--------+-----------+    +--------+----------+    +--------+----------+
           |                         |                         |

                                     |
           +-------------------------+-------------------------+
           |              FastAPI Backend (:8000)             |
           |                                                   |
           |  Endpoints:                                       |
           |    POST /ask           -- semantic search         |
           |    POST /chat          -- conversational search   |
           |    GET  /auth/login    -- start OAuth flow        |
           |    GET  /auth/callback -- handle OAuth callback   |
           |    POST /emails/sync   -- pull Gmail messages     |
           |    POST /emails/seed   -- load mock data          |

           |    GET  /ready         -- Railway health probe    |
           |                                                   |
           +-----------+-------------------+-------------------+
                       |                   |
           +-----------+--------+  +-------+------------------+
           |  MongoDB Database  |  |    Google External APIs  |
           |  (local or Atlas)  |  |                          |
           |                    |  |  - Gmail REST API        |
           |  Collections:      |  |  - Google OAuth 2.0      |
           |    emails          |  |  - Gemini API            |
           |    settings        |  |    (gemini-2.5-flash)    |
           +--------------------+  +--------------------------+

Request Flow — Semantic Search:
  1. User types query in web dashboard or Chrome extension popup.
  2. Frontend POSTs { query, k } to /ask.
  3. Backend calls Gemini API to extract structured intent from the query:
       { search_query, keywords, sender, date_hint, topic }
  4. Backend encodes search_query using local SentenceTransformer model.
  5. Cosine similarity is computed against all stored email embeddings.
  6. Keyword boost (+0.15 per match) applied if Gemini extracted keywords.
  7. Top-K results sorted by final score and returned as JSON.
  8. Frontend renders result cards with relevance percentage bars.

Request Flow — OAuth + Email Sync:
  1. User clicks "Connect Gmail" → GET /auth/login.
  2. Backend creates OAuth flow, stores in memory dict, redirects to Google.
  3. User consents → Google redirects to /auth/callback with auth code.
  4. Backend exchanges code for credentials, stores token + gmail address
     in MongoDB settings collection.
  5. User triggers sync → POST /emails/sync.
  6. Backend fetches up to 500 message IDs from Gmail API.
  7. For each message, fetches full payload, walks MIME tree, extracts text.
  8. Computes 384-dim embedding per email via SentenceTransformer.
  9. Upserts document into MongoDB emails collection.

5. BACKEND DESIGN
================================================================================

The backend is a single-file FastAPI application (main.py) with supporting
modules for database access (db.py), embedding operations (embeddings.py),
and AI-assisted query processing (agent_search.py).

--- main.py ---
Defines all HTTP endpoints and orchestrates business logic:

  GET  /health
    Returns {"ok": true, "database": "up/down"} — used by monitoring.

  GET  /ready
    Railway health probe endpoint. Returns 200 when the app is ready
    to serve traffic. Designed with a 300-second timeout to accommodate
    slow PyTorch model warm-up.

  GET  /auth/login
    Initiates Google OAuth 2.0 flow. Generates authorization URL with
    scopes: gmail.readonly, userinfo.email. Stores flow object in memory
    dict keyed by a random state parameter. Redirects browser to Google.

  GET  /auth/callback
    Handles Google's redirect after user consent. Exchanges auth code for
    credentials. Fetches user's Gmail address from Google userinfo API.
    Stores oauth_token and gmail_address in MongoDB settings collection.

  POST /emails/sync
    Authenticates using stored token. Calls Gmail API messages.list with
    maxResults=500. For each message ID, fetches full payload (format=full).
    Parses MIME tree recursively to extract text/plain content (skips
    attachments). Generates embedding using local SentenceTransformer.
    Upserts document into emails collection with fields:
      id, threadId, subject, sender, date, body (2000 char cap),
      snippet, account (gmail address), embedding (list of 384 floats).

  POST /emails/seed
    Loads mock email data from emails.json file. Computes embeddings for
    each entry. Upserts into MongoDB. Used for demo/testing without
    real Gmail credentials.

  POST /ask  (QueryRequest: { query: str, k: int = 5 })
    Main semantic search endpoint. Calls agent_search.extract_query_intent()
    to parse user query via Gemini. Encodes resulting search_query with
    SentenceTransformer. Fetches all email documents from MongoDB. Computes
    cosine similarity between query vector and each email's embedding.
    Applies keyword boost (+0.15 per keyword found in email text).
    Returns top-k results sorted by score.

  POST /chat  (ChatRequest: { message: str, history: list, k: int = 5 })
    Conversational variant of /ask. Passes full conversation history to
    Gemini so follow-up queries resolve correctly (e.g., "narrow to
    last month" understands context from prior turn). Returns results
    with the same ranking pipeline as /ask.

--- embeddings.py ---
  - _model: module-level cache variable (None until first use)
  - get_model(): lazy-loads SentenceTransformer('all-MiniLM-L6-v2')
  - encode(text): returns L2-normalized 384-dim numpy array
  - cosine_similarity(a, b): dot product of two normalized vectors
  - warmup(): fire-and-forget background thread that calls encode("warmup")
    on startup to pre-load PyTorch so first real request is fast

--- agent_search.py ---
  - Uses google.generativeai SDK with gemini-2.5-flash model
  - System prompt instructs Gemini to extract structured search intent
  - Input: raw user query + optional conversation history
  - Output: JSON with fields:
      search_query  -- cleaned query for embedding
      keywords      -- list of salient terms for boosting
      sender        -- extracted sender name/email if mentioned
      date_hint     -- temporal reference if mentioned
      topic         -- subject category
  - If GEMINI_API_KEY is absent or API call fails, returns passthrough
    object with search_query = original user query (graceful fallback)

--- db.py ---
  - Async MongoDB connection using motor.motor_asyncio
  - Reads MONGODB_URI from environment (default: mongodb://127.0.0.1:27017)
  - Reads DB_MAIL from environment (default: mail_sherlock)
  - Exposes: db.emails, db.settings collections

7. CHROME EXTENSION
================================================================================

The Chrome extension provides quick access to Mail-Sherlock search without
leaving Gmail. It is built as a Manifest V3 extension with three separate
JavaScript bundles, each with its own Vite config:

--- Popup (MinimalPopup.tsx) ---
  - Small React UI that opens when the extension icon is clicked
  - Shows connection status indicator (connected / offline)
  - Search input field with submit on Enter
  - Displays result cards: subject, sender, score percentage
  - Each result links directly to the email thread in Gmail
    (https://mail.google.com/mail/u/0/#inbox/{threadId})
  - Uses Chrome Storage API to persist panel open/close state

--- Content Script ---
  - Injected into mail.google.com pages
  - Can read DOM context for integration with Gmail UI (e.g., detecting
    currently open email for context-aware search)

--- Background Service Worker ---
  - Persistent background script (MV3 service worker)
  - Acts as API proxy: relays search requests from content script to
    the local backend (localhost:8000)
  - Handles cross-origin requests from the extension to the API

--- Manifest V3 Notes ---
  - Permissions: storage, tabs, scripting
  - Host permissions: http://localhost:8000/*, https://mail.google.com/*
  - Hardcoded to 127.0.0.1 (not localhost) to avoid Windows IPv6 issue
    where Node/Chrome resolves localhost to ::1 but uvicorn listens on IPv4

8. AI & MACHINE LEARNING PIPELINE
================================================================================

--- Embedding Model: all-MiniLM-L6-v2 ---
  - Source: HuggingFace sentence-transformers library
  - Architecture: MiniLM (distilled BERT), 6 transformer layers
  - Output dimensionality: 384 floats per text input
  - Model size: ~90MB (cached locally after first download)
  - Normalization: L2-normalized output (unit vectors)
  - Similarity metric: dot product == cosine similarity (after normalization)
  - Inference: CPU-only (no GPU required)
  - Latency: ~20-80ms per encoding (varies by text length and CPU)

Why all-MiniLM-L6-v2?
  - Fast on CPU compared to larger models (BERT-base, MPNet)
  - Good semantic quality for sentence-level similarity tasks
  - Small enough to distribute with a consumer-grade Python app
  - No API key required; fully offline after download

--- Indexing Pipeline ---
  1. Raw email text = f"{subject}. {body[:2000]}"
  2. encode(text) → 384-dim numpy array (L2-normalized)
  3. Stored as list of floats in MongoDB document

--- Search Pipeline ---
  1. User query → Gemini extraction → refined search_query string
  2. encode(search_query) → query_vector (384-dim)
  3. For each email document: score = dot(query_vector, email_embedding)
  4. Keyword boost: for each keyword in Gemini output, if keyword found
     (case-insensitive) in subject+body, score += 0.15
  5. Sort descending by score; return top-k

--- Gemini Integration (gemini-2.5-flash) ---
  - Role: Natural language understanding layer (not email content processor)
  - Input: User's raw query text (max ~200 tokens typical)
  - Output: Structured JSON intent object
  - Temperature: 0 (deterministic, reproducible results)
  - Max output tokens: 512
  - System instruction: Instructs model to extract search_query, keywords,
    sender, date_hint, topic as JSON
  - Privacy: Only the user's query is sent to Gemini, never email content
  - Fallback: If GEMINI_API_KEY missing or call fails, passthrough to raw
    embedding search with original query string

--- Score Interpretation ---
  Raw cosine similarity ranges from -1 to 1, but in practice:
    - 0.80+ : Very strong match (visually: purple in UI)
    - 0.65-0.79 : Good match (visually: pink in UI)
    - 0.50-0.64 : Moderate match
    - Below 0.50 : Weak match
  Keyword boost can push borderline results into higher tiers.

--- Model Warm-up Strategy ---
  PyTorch imports and model loading (~2-4 seconds on cold start) are
  deferred until first use. On application startup, a fire-and-forget
  background thread calls encode("warmup") so that by the time the first
  real user request arrives, the model is already loaded into memory.
  This prevents Railway health probes from timing out while also keeping
  the API responsive immediately after startup.

9. GMAIL INTEGRATION & OAUTH
================================================================================

Authentication uses Google OAuth 2.0 with offline access (refresh tokens).

Scopes requested:
  - https://www.googleapis.com/auth/gmail.readonly
  - https://www.googleapis.com/auth/userinfo.email

Flow:
  1. Client credentials loaded from GOOGLE_CREDENTIALS_JSON env var or
     credentials.json file (downloaded from Google Cloud Console).
  2. InstalledAppFlow creates an authorization URL with state parameter.
  3. Flow object stored in memory dict (_flows[state] = flow).
  4. User visits URL, consents, redirected to /auth/callback?code=...&state=...
  5. Backend fetches flow from memory using state, exchanges code for token.
  6. Token (includes access_token, refresh_token, expiry) stored as JSON
     string in MongoDB settings: {"key": "oauth_token", "value": "..."}.
  7. Gmail address fetched from Google userinfo endpoint and stored
     in settings: {"key": "gmail_address", "value": "user@gmail.com"}.

Email Fetching:
  - gmail.users().messages().list(userId='me', maxResults=500)
  - For each message ID: gmail.users().messages().get(id=id, format='full')
  - MIME parsing via recursive walk of payload.parts tree:
      * Stops at text/plain parts (no filename — not an attachment)
      * Decodes base64url encoded body data
      * Falls back to payload.body.data if no parts tree
  - Extracts: id, threadId, subject (from headers), from (sender),
    date (from headers), body text (capped 2000 chars), snippet

Token Refresh:
  - google-auth library handles token refresh automatically via
    credentials.refresh() when access token expires
  - Refresh token persisted in MongoDB, so user does not need to
    re-authenticate after session expiry

Multi-account Support:
  - Architecture supports multiple accounts (account field on each email)
  - Current implementation: one active OAuth token stored in settings
  - UI shows multiple accounts in sidebar with color dots
  - Full multi-account parallel sync is planned (see roadmap)

10. DATABASE DESIGN
================================================================================

Database: MongoDB (mail_sherlock)

--- emails collection ---
Each document represents one Gmail message:
  {
    "_id": ObjectId,
    "id": "gmail_message_id",         -- Gmail's unique message ID
    "threadId": "thread_id",          -- for Gmail deep link URL
    "subject": "Meeting notes...",
    "sender": "alice@example.com",
    "date": "Mon, 15 Jan 2026 ...",
    "body": "Hi, following up on...", -- truncated to 2000 chars
    "snippet": "Short preview...",    -- Gmail-provided snippet
    "account": "user@gmail.com",      -- which Gmail account
    "embedding": [0.023, -0.145, ...] -- 384 floats (L2-normalized)
  }
  Upsert key: { "id": gmail_message_id }
  Index: (none explicit; full collection scan on each search)
  Typical size: ~500 documents per account, ~1.5KB per document

--- settings collection ---
Key-value store for configuration:
  { "key": "oauth_token",    "value": "{...json...}" }
  { "key": "gmail_address",  "value": "user@gmail.com" }
  Upsert key: { "key": field_name }

Notes:
  - Embeddings stored as plain arrays (not using MongoDB Atlas Vector Search)
  - Similarity computed in Python (NumPy), not in DB query
  - This approach works well at the current scale (~500 emails)
  - At larger scale (10k+ emails), Atlas Vector Search or FAISS would be
    more appropriate

12. SECURITY & PRIVACY
================================================================================

Privacy:
  - Email content NEVER sent to any external AI service
  - Embeddings computed 100% locally on user's machine
  - Only the user's natural language query (not email text) is sent to Gemini
  - All email data stored in user's own MongoDB instance

OAuth Security:
  - OAuth tokens stored in MongoDB (encrypted at rest via Atlas if configured)
  - No tokens logged or exposed in API responses
  - Google credentials loaded via environment variable (not hardcoded)
  - Offline access scope allows background refresh without user interaction

Current Weaknesses (known, to be addressed):
  - CORS: allow_origins=["*"] — accepts requests from any origin
    (fine for localhost dev; should restrict to extension/web origins in prod)
  - OAuth state stored in memory — app restart during OAuth flow breaks auth
    (state dict lost; user must restart the flow; planned fix: store in MongoDB)
  - Email body stored as plaintext in MongoDB — at-rest encryption depends
    on MongoDB configuration (Atlas can enable encrypted storage)
  - MONGODB_TLS_INSECURE env var allows disabling TLS — dev-only, not for prod

Extension Permissions (least-privilege):
  - Only requests storage, tabs, scripting
  - Host permissions limited to localhost:8000 and mail.google.com
  - No access to other websites or browser history

14. KNOWN LIMITATIONS & FUTURE ROADMAP
================================================================================

KNOWN LIMITATIONS:

  1. Full collection scan on each search
     All embeddings are loaded from MongoDB and similarity computed in Python
     for every search request. At 500 emails this is fast (<100ms), but
     would degrade at tens of thousands of emails.
     Fix: MongoDB Atlas Vector Search, or in-process FAISS index.

  2. OAuth state in memory
     The OAuth flow object is stored in a dict in the Python process. If the
     server restarts between /auth/login and /auth/callback, the state is
     lost and the auth fails. Fix: persist state in MongoDB with a TTL index.

  3. Chat history not persisted
     Conversation history passed in /chat requests is session-only (stored
     in React state). Refreshing the browser loses history.
     Fix: persist chat sessions in a MongoDB chat_sessions collection.

  4. Single active Gmail account
     The settings collection stores one oauth_token and one gmail_address.
     Full multi-account support requires a list-based data model keyed by
     account ID.

  5. No attachment indexing
     Only text/plain MIME parts are indexed. PDF, Word, image attachments
     are skipped. Fix: integrate Apache Tika or PyPDF2 for attachment parsing.

  6. Embedding stored as plain array
     384 floats per email stored in MongoDB as a JSON array. This is
     convenient but not storage-efficient (no compression, no native
     vector type). Fix: use BSON binary or Atlas Vector Search native fields.

FUTURE ROADMAP (from instruction.md):

  Phase A — Scale & Robustness
    - Expand sync to 300+ messages with incremental sync (skip already-indexed)
    - Improve MIME parsing for more complex attachment structures
    - Add error handling for quota exceeded / rate limit from Gmail API

  Phase B — Hybrid Search
    - Integrate rank-bm25 library for BM25 keyword scoring
    - Implement Reciprocal Rank Fusion (RRF) to blend BM25 and cosine scores
    - A/B test against current keyword-boost approach

  Phase C — Conversational UX
    - Persist chat sessions in MongoDB (chat_sessions collection)
    - Add session management UI (list of past searches, continue a session)
    - Streaming responses for long Gemini outputs

  Phase D — Performance & Quality
    - Embedding cache: store hash of email text; skip re-embedding if hash
      matches (avoids redundant inference on re-sync)
    - Rate limiting with slowapi
    - Automated evaluation: curated query/expected-result pairs,
      recall@k and MRR metrics
    - Pre-bake SentenceTransformer model into Docker image for instant startup
